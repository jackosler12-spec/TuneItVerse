# TuneItVerse v3.47.0 — capability matrix, sourced ECU DB, real TunerPro XDF parser, offline UX

## v3.47.0 changes (2026-10-21)

### 1. ECU database (index 1.26, 16 families)
- Every family now carries `capabilities` for `identify`, `read`, `checksum`, `seed_key`, `write`, `map_hints`. Each one has a `status` from a fixed enum (`verified_dump`, `verified_log`, `public_source`, `reference_doc`, `experimental`, `report_only`, `unverified`, `not_supported`) and a `source`. Every entry has `hardware_tested: false`.
- A schema-validated loader (`validate_entry` / `validate_index`) drops invalid entries and reports them in Self-check. Tests enforce source and status on every capability. They also enforce that only `P01_0411` has a checksum corrector and that nothing is marked hardware-tested.
- **GM_P59 corrected:** it is 1 MiB, not 512 KiB (PcmHammer `PcmInfo.cs` @033cb03). Unsourced map addresses and OS IDs were removed.
- **New families GM_P10 and GM_P12:** identify-only, sourced from PcmHammer `PcmInfo.cs`. Their size and key-algorithm index are public source. There is no checksum, read or write.
- **New `gm_osid_map.json`:** 2618 GM OS IDs mapped to a PCM type, generated by `scripts/gen-gm-osid-map.mjs` from the same pinned `PcmInfo.cs`. `identify_bin` now reports the OS ID, the PCM type and the source.
- P59 OS IDs `12579405` and `12587603` were wrongly listed as P01 markers. They are removed. The P01 checksum corrector now refuses any OS ID the map lists as a non-P01 GM type.
- `identify_bin` no longer reports EDC16C41 as `correction_safe` or `write_allowed`. `correction_safe` is true only for corrector families, and `write_allowed` follows the live write gate.
- Size-catalog map hints that have no citation are labelled `UNVERIFIED hint (no cited source)`.

### 2. Offline tools
- **Real TunerPro XDF parser** (`parse_tunerpro_xdf`, `parse_xdf_report`), checked against TunerPro help and RomRaider's XDF conversion layer:
  - Reads XDFTABLE and XDFCONSTANT.
  - Subtracts BASEOFFSET when `subtract` is set.
  - Reads 1-based CATEGORYMEM.
  - Handles the `mmedtypeflags` signed, LSB-first and column-major bits.
  - Uses axis LABELs as headers.
  - Float cells, strided layouts, unsupported cell sizes and items with no address are **skipped and listed**. The Maps page shows the skipped count. They are never guessed.
- **Scaling math evaluator** for `+ - * / ( )`, unary minus and numbers. Patches are written only when the equation is verified linear. Non-linear math, ragged grids and shape mismatches are refused. The old path silently wrote physical values as raw.
- The TableData parser no longer invents a fallback address (`0x8000+i*0x100`) for tables that have none.
- BIN workflow:
  - Correct CS and script results now reach Save BIN (`setWorkingBin`). Before this, overlays wrote a `window.currentBin` that Save never read.
  - Unsaved-changes guard on both the window close (native dialog) and reload.
  - Recent files (bin/xdf/a2l/csv; extension and 16 MiB checks).
  - Cells are highlighted against the loaded BIN and the reference BIN.
  - Patching a table marked UNVERIFIED asks for confirmation.
- Lost controls are restored in `index.html`: reference/cell delta, BIN undo/redo, smooth/interp/copy/paste/clamp/%/STFT, hex poke, flash Compare/Verify/write gates, and the log studio panel.

### 3. Identification and checksums
- P01 CS1/CS2 stay the only corrected checksums (verified on the reference image and on the private dump through `TIV_P01_BIN`).
- EDC16C41 stays report-only.
- Non-P01 GM images are refused by the P01 corrector, with the PCM type named in the message.

### 4. Capability surface
- New **Capabilities** view and a per-BIN capability strip, driven by the `family_capabilities` command.
- The flash catalog labels P01 write "experimental write (off by default, not bench-tested)". The old 'LIVE' label is gone.
- **No new write path.** The experimental P01 kernel write remains behind its existing flag and typed confirm.

### 5. UX
- New Inspect and Compare views, plus a status bar (family / OS / size / dirty / version).
- Keyboard shortcuts:
  - Ctrl+O open, Ctrl+S save.
  - Ctrl+Alt+Z / Y undo / redo.
  - Alt+1..0 switch pages.
  - Ctrl+F filter tables.
  - F1 or `?` shows help.
- `npm test` now runs `scripts/check-frontend.mjs`. It checks script syntax and tags, that every invoked command is registered in Rust, that every bound button id exists, that ids are unique, that nav panels exist, and that version strings agree.

**Tests:** `cargo test --lib` 329 passed (304 at v3.46.1). They also pass with `TIV_P01_BIN` set to a private P01 dump. `npm test` passes.

**Unverified in v3.47.0:**
- Nothing in this release was bench-tested and no hardware path was exercised.
- P10/P12/P59 are identify-only.
- The XDF parser does not handle float cells, strided layouts or embedded axis data (axis LABELs only).
- Catalog map hints stay unverified.
- Nissan DID meanings stay unknown.
- The raw-VPW send path is still wrong.
- No Windows exe was built for this change (the work was done on Linux; CI builds and tests on Windows).

## v3.46.1 — Nissan session blocks, real F190/F18C frames, re-init fallback

## v3.46.1 changes (2026-10-20)
Source: Data Logger extra frames #2 (`reference/fixtures/elm_patrol_session_identity.txt`, 7E8 frames only).

1. **F190/F18C.** The test now uses the real 26 Jun frames. On the Patrol both get `7E8 03 7F 22 12` inside 10C0. `22F190` sent to 7DF outside a session got NO DATA. Correction to v3.46.0: the ECU never sent `7F 22 11`; that reply came from the BCM on 765.
2. **Nissan session blocks.** Every positive 2211/12/13xx read in the log was inside 10C0 sent to 7E0, so 10C0 is still required. The raw DID poll now copies Car Scanner's blocks. A block opens with ATSH7E0 + `10C0` (`10C01` once the CAN protocol is known), polls `NISSAN_BLOCK_SAMPLES` (4) samples, then closes with `1081(1)` + ATSH7DF. Log stop and disconnect also close the block. The block length is an approximation of the log: about 44 exchanges per block in the 20 May session. If the ECU drops the session (`7F xx 7F` / `7F xx 22`), 10C0 is re-sent mid-block. The `7F 22 7F` in that test is synthetic. Any error path sends 1081 + ATSH7DF through the Drop guard.
3. **Re-init.** Bare STCAF1, STFAC and ATCRA were never seen answered on the MX+. They stay in the list, but a `?` reply is now logged in the session (`recovery_log`) and ignored. ATFCSM0 stays (979 OKs on the Patrol). If the 2D1/23D flood survives the re-init, the app falls back to ATZ + full warmup + defaults and retries once.
4. **Late answer.** The real 24 Aug sequence `>190208\r7E8037F1978\r\r>1902AC\r7E8035902FF\r\r>` is a test: the `59 02 FF` in the 1902AC reply is reported as ambiguous. The test for an answer arriving after the prompt is labelled synthetic; the Data Logger found no such case in any session.
5. **1143 / 120B.** The DB now says "advertised in mask, never read; length unknown". These are read only singly, with a 1..=8 byte check, and the length they return is reported, not assumed.

**Unverified in v3.46.1:** replay-tested only. The block length is an approximation. The session-drop NRC test is synthetic. A physical 7E0 read without 10C0 was never tried in the log.

## v3.46.0 — Nissan DID reads, adapter cleanup, response-pending handling

## v3.46.0 changes (2026-10-20)
Source: further redacted frames from the same Car Scanner/OBDLink log (Data Logger agent). Committed fixtures: `reference/fixtures/elm_patrol_nissan_22reads.txt` (18 KB slice of the 2.6 MB read dump, ECU 7E8 frames only) and `reference/fixtures/elm_cleanup_and_pending.txt` (13 KB). The full dump is not committed.

1. **Support masks.** Tested: the 2211xx/2212xx/2213xx masks decode to exactly the 30 DIDs Car Scanner polled plus 1143 and 120B (MSB of the first byte = base+1). No code change was needed.
2. **DID value reads.** DID lengths as observed: 1101–1147 one byte, 1207–130E two bytes. 1143/120B were never read, so their length is unknown and they are read one at a time. Reads go 3 DIDs per request; every DID echo and length is checked. Any multi-read failure (`7F 22 23`, `7F 22 21`, NO DATA, mismatch) falls back to single reads. A single `7F 22 21` is retried once. Optional log channels `nissan_XXXX` ("Nissan DID XXXX (unknown meaning, raw)", off by default) log the raw big-endian value. The EDC16C41 DB entry has `nissan_did_observations` (length, min/max raw, distinct values, read counts, meaning "unknown"). F190/F18C are probed and reported as "not supported (NRC ..)". Their bytes are never stored. Replay strips Car Scanner's frame-count suffix (`221101110211042` → `22110111021104`).
3. **Adapter cleanup.** A Drop guard restores adapter state on every exit, error or not. The ELM ISO-TP path restores `ATCAF1 ATH1 ATSH7DF`. The Nissan scan and poll restore `1081 ATSH7DF`. Replies that carry CAN frames from non-OBD IDs (the 11 Aug `2D1`/`23D` flood after `STCAF0` + `ATCM000`) trigger a re-init (`ATCAF1 STCAF1 ATCRA ATAR ATFCSM0 STFAC ATSH7DF ATH1 ATS0 ATST96`). A valid 7E8 answer in the same reply is used; otherwise there is one retry. Foreign frames are never decoded. `NO DATA` on the ISO-TP path is an error (it used to hex-decode to `0xDA`).
4. **7F xx 78 after the prompt.** After a response-pending, the app keeps listening for up to P2* (5 s) without sending anything, even after the `>`. If an ECU is still pending when that window ends, its answer to the next request with the same SID is reported as ambiguous and discarded. Answers are matched per ECU by SID and PID/DID echo, so a stray `59 02 FF` is never taken as the answer to another request. Tests use the real multi-ECU `19 02 xx` transcripts and the Patrol `0902` case.

**Unverified in v3.46.0:** replay-tested only, nothing has run on a live car from this build. DID meanings and scaling are unknown. The late-answer-after-prompt case is a synthetic test, because the log has no example of it. Two lengths are unknown: 1143 and 120B. Not every adapter supports `STCAF1`/`STFAC`/`ATFCSM0` (an unknown command answers `?` and is ignored). The F190/F18C NRCs come from the Data Logger's report and are not in the committed fixtures (corrected in v3.46.1: both are 7F 22 12 from the ECU).

## v3.45.0 — ELM/OBDLink live-data fixes from a real Patrol log

## v3.45.0 changes (2026-10-20)
Source: Jack's Car Scanner + OBDLink MX+ log from his 2007 Nissan Patrol GU ZD30CRD (CAN 11-bit 500k), via the Data Logger agent. Only redacted adapter frames are committed (`reference/fixtures/elm_patrol_zd30_obdlink.txt`).

1. **ELM reply parsing fixed.** With `ATH1` the old parser joined all hex and cut pairs, so the `7E8` header shifted every byte and real replies (`7E804410C0BBC`, `7E80441230CF6`, `7E803410550`) decoded to nothing. `elm_parse.rs` now parses per line: strips 11-bit/29-bit CAN or 3-byte J1850/KWP headers, follows the ISO-TP PCI (single, first, consecutive frames), keeps waiting on `7F xx 78`, reports other `7F` NRCs, `NO DATA` and adapter errors (`CAN ERROR`, `STOPPED`, `BUFFER FULL`, `?`) as errors. Text like `SEARCHING...` no longer leaks hex letters.
2. **Live data deadlock fixed.** `transport::current_protocol()` re-locked the global STATE mutex while `with_port` already held it, so every live read (dashboard, logging, read_properties) would hang. The protocol now lives in the transport session cache.
3. **Supported-PID polling.** Reads and caches 0100/0120/0140... per session and polls only listed PIDs. Added SAE PID 0x23 fuel rail gauge pressure ((A*256+B)*10 kPa) and 0x21. The Diesel OBD template now includes rail (it is a standard PID).
4. **Timing.** 1000 ms read window (adapter `ATST96` = 600 ms), 6 s for the first request (protocol search), response-count suffix (`010C1`) once CAN is confirmed, read no longer ends on a serial timeout before the prompt, STPTO 600 instead of 100. Logging stops after 10 consecutive NO DATA with "ignition off?".
5. **Adapter state.** `elm_init_can_500k` no longer sends a second `ATZ` (it wiped the OBDLink setup). Mode 01 restores `ATCAF1 ATH1 ATS0 ATST96` after ISO-TP code switched to `ATCAF0`.
6. **Voltage.** Adapter STVR/ATRV first; PID 0x42 only when the ECU lists it (the Patrol does not). The UI/audit label is the real source (`adapter_stvr`, `adapter_atrv`, `pid42`, `pid42_vpw_raw`); it used to say `pid42` for adapter readings. Raw VPW frames are no longer written to ELM ports as a fallback.
7. **Nissan CAN diagnostic path (read-only).** `ATSH7E0`, `10C0`→`50C0`, `2211xx/2212xx/2213xx` support masks, optional raw `22xxxx` reads, always `1081` + `ATSH7DF`. The 32 IDs seen on the Patrol are listed as "supported, meaning unknown". No names or scaling assigned. Old K-line Consult code is marked UNVERIFIED.
8. **CSV import.** Car Scanner long format (`SECONDS;PID;VALUE;UNITS;LATITUDE;LONGTITUDE`) is pivoted per timestamp; GPS columns are dropped in all imports.
9. **Replay transport.** `replay_port.rs` replays the fixture as a serial port so CI covers warmup/text-mode setup, support masks, Mode 01 polling, Mode 09 (cal ID, blank VIN), ATRV and the Nissan scan. J1850 VPW frames from the same log verify CRC-8; `vpw::validate_frame` now accepts the real J1850 CRC-8 on received frames.
10. **Fingerprint.** The Patrol reports cal ID `0VS43B`, an all-zero VIN and `090A` NO DATA. Nothing confirms EDC16C41; the DB marks the vehicle mapping **unconfirmed** and `read_properties` shows EDC16C41 only as `candidate_family`.
11. Connect screen: Adapter Status / Bus Monitor buttons now exist and their script is loaded (it was not), plus Supported PIDs and Nissan CAN Scan.

**Unverified in v3.45.0:** none of this has run against a live car from this build; it is tested on replayed real frames only. ISO-TP flow control on multi-frame replies is left to the adapter (ATCAF1). Nissan data-ID meanings are unknown. Raw-VPW TX still appends an additive byte, not the J1850 CRC (ELM/STN adapters add the CRC themselves). The `vpw` protocol option sets up an OBDLink with STP 12 but then sends raw binary frames; that path needs a separate look.
